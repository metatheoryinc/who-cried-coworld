# Dead chat (the Graveyard) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Dead players get a Graveyard chat. Dead humans can post at any time; one dead AI answers each human
message. The living never see it. No model calls unless a dead human is talking.

**Architecture:** A new event (`dead_chat`) with a new audience (`{kind:'dead'}`) that `project()` resolves against the
journal's eliminations, so living seats can never receive it. `HumanSession` keeps Graveyard requests in their own
map (`ghosts`), separate from the phase's `pending`, so phase timing, tallies and scores never see them. The server
finds a seat's open request through `session.requestFor(slot)`. Responder choice: named AI, else the LLM host's pick
(a second host function sharing the moderator's inference), else a seeded random dead AI.

**Tech Stack:** TypeScript, Zod, Vitest. Node 24 (`export PATH=~/.nvm/versions/node/v24.19.0/bin:$PATH`).
Design: `docs/plans/2026-10-02-dead-chat-design.md`.

Run all tests: `npx vitest run`. Typecheck: `npx tsc --noEmit -p .`.

### Task 4: HumanSession — Graveyard chat, ghost requests, responder choice

**Files:**
- Modify: `src/game/runtime/session.ts` (`requestFor(slot)`; `observation`/`receive` use it)
- Modify: `src/game/runtime/human-session.ts`
- Modify: `src/game/domain/moderator.ts` (ghost host types, prompt, validation)
- Test: `tests/runtime/dead-chat.test.ts`

Behaviour:
- `chat(slot, {channel:'graveyard'})`: human, dead, game started and not finished; any period. Emits `dead_chat`
  with audience `dead`. Existing 30-per-phase / 2-second limits apply (key includes the channel).
- After a human Graveyard message: if no ghost request is outstanding and fewer than 6 AI replies were requested
  this phase, pick a responder among dead AI seats:
  1. named in the message (`mentionsName` against all roster names);
  2. else `ghostHost(input, signal)` if set, within 2 s, validated (must be a dead AI slot);
  3. else seeded random: `draw(seed, 'graveyard', n, deadAi.length)`.
- A ghost request: `openRequest({..., deadline: now+15000, request:{kind:'dead_chat',maxCharacters:240}})` in
  `ghosts`. `requestFor(slot)` returns `pending.get(slot) ?? ghosts.get(slot)`.
- `receive` for a ghost: `submit()`; on accept, emit the reply as `dead_chat` (if text non-empty) and delete it.
  Rejections and timeouts drop silently: no failure events, no tallies.
- `advance(now)`: drop ghosts past their deadline. The reply count resets when the period changes.
- Snapshot: `channels` adds `graveyard` for a dead human; `chatEnabled` is true for a dead human until the result;
  `revealedRoles` is filled for a dead human (the ghost's view).
- `disconnect` closes a ghost silently.

Tests:
- A dead human's message to a named dead AI opens exactly one `dead_chat` request for that AI; its observation has
  `self.alive:false` and contains the message.
- The AI's reply is published to the dead and never to living seats.
- A second human message while a reply is outstanding opens no new request; at most 6 replies per phase.
- No message, no request: a full game with a dead human who never types has no `dead_chat` requests.
- Without a host and no name, the pick is a dead AI and is reproducible for the same seed.
- With a host, its valid pick is used; an invalid or slow pick falls back to random.
- A living human cannot post to the Graveyard; a dead human cannot post to Town.
- A rejected or expired ghost reply leaves `valid_actions` and failure events unchanged.
- Dead human snapshot has all roles; living human snapshot has none before the result.

Commit: `Graveyard: dead chat in human games, one AI reply per human message`.
